# 0.9.0 notification activation fix verification

Date: 2026-10-17. Tracking: #174; parent release validation: #171.
Base: `92ddd1c1464e0b5b8d29d0e6aac3c3eb847d355f` on `prerelease/0.9.x`.
This record covers the activation repair; the earlier failed real-toast
observations on #171 remain valid historical evidence.

## Reproduction and repair

Windows could not cold-start the registered native callback class. Both the
agent's direct native probe and the operator's Windows PowerShell 5.1 probe
returned `0x80040154` with no COM object. Starting the existing signed helper
with `-Embedding` made native COM activation and callback delivery succeed.
The reason Windows rejects cold activation remains unresolved.

The extension now owns two callback helpers while notification correlations
remain. It renews alternating helpers every 25 seconds, retaining the previous
registration for a two-second overlap. The pinned helper exits after a callback
or 60 seconds ([KDE source](https://github.com/KDE/snoretoast/blob/v0.9.0/src/snoretoasts.cpp),
fetched 2026-10-17). This removes reliance on cold activation while the owner is
open; it does not repair Windows COM registration.

No native binary or runtime dependency changes. Helpers remain scoped to their
extension host and callbacks retain their owning pipe/session correlation.
Normal disposal terminates owned helpers; failed termination is reported and
ownership retained for a later disposal attempt or the helper's native expiry.
The existing seven-day correlation expiry bounds abandoned notification state.

## Native protocol evidence

The isolated run of [the native smoke test](../../test/manual/snoreToastActivation.smoke.cjs)
completed at 23:19:37 UTC. It rejected external SnoreToast processes before
startup and before each COM activation. The earlier standalone diagnostic pool
was stopped before this run.

- Four initial helpers renewed; four owned replacement helpers remained live
  after waiting 65 seconds.
- Four direct native COM activations returned `0x00000000` through
  [the callback probe](../../test/manual/invokeSnoreToastCallback.ps1).
- Live callbacks selected the correct synthetic owner/session across two pipes.
- Closed-session and closed-owner callbacks did not activate another session.
- Eleven owned helpers started across renewal and callback replacement; zero
  remained after cleanup.

This is native protocol/lifecycle evidence. It does not display a real Windows
toast, exercise a real Claude prompt, or establish foreground/taskbar behavior.

## Manual acceptance still required

session activation or VS Code selection. The corrected host was running with
its attention channel ready and a supported managed session. The original
debug log did not record successful native emission or callbacks, so it cannot
distinguish a delivery failure from a focus failure. No helper was running at
inspection afterward; this alone does not establish whether the final callback
had been consumed. Fresh-toast/live-question confirmation is pending. See
[the retest record on #174](https://github.com/glitchwerks/vscode-claude-workspaces/issues/174#issuecomment-6279402627).

Targeted debug records now distinguish launch requests, matched or unmatched
callback actions, panel-focus requests/completion and session activation. They
exclude notification content and raw callback payloads; unknown actions are
reported only as `unknown`. A successful panel-focus command still does not
establish Windows foreground activation. The failed manual result remains open.

Each of the four extension-host configurations passed 91 tests (364 total),

the logger now confirms the target session is active before recording activation.
Independent review found no remaining diagnostic issues. These checks validate
instrumentation and do not change the failed real-toast result.
