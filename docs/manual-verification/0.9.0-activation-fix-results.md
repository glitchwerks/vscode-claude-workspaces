## PR review: closed-session helper cleanup (2026-10-21)

[Review comment 4343417870 on PR #175](https://github.com/glitchwerks/vscode-claude-workspaces/pull/175#discussion_r4343417870)
identified a resource-lifecycle gap after the manual acceptance run. The
registry pruned only expired correlations, and session closing/removal never
cancelled them. A stale click could safely do nothing while its unconsumed
registration still kept the helper pool renewing for up to seven days.

The registry now prunes correlations whose managed session is closing or no
longer owned. The host reconciles that state on session lifecycle changes,
immediately releasing the helper pool and scheduled work when no live pending
registrations remain. Another live session retains callback renewal, banner
fade remains selectable, and the live seven-day correlation expiry is unchanged.

Before the production fix, the registry/activator regression run had 18 passes
and three expected failures: a faded closed-session registration stayed pending,
a closed target still routed, and a lifecycle update did not stop an active
pool including its overlapping worker. Two real VS Code 1.128.0 host regressions
also failed because both helpers stayed alive after explicit closing or process
exit. After the fix:

- The focused registry/activator/sink/selection suites passed 51 tests. Coverage
  includes cancellation without a click, cancelled-ID non-revival, live-session
  isolation, immediate worker/timer cleanup including overlap, pool restart for
  a later live notification, and the unchanged seven-day live delayed-click
  contract. The isolated registry/activator subset passed 22 tests.
- `npm run check:types` and `npm run lint` passed.
- `npm run test:integration` passed 95 tests in each of the four saved-workspace
  and folder-window configurations on VS Code 1.128.0 and 1.136.1 (380 total).
  Its new cases exercise real host wiring, a banner-timeout callback, cleanup
  before a closing PTY reports exit, process exit, and harmless stale
  callback rejection after cancellation.
- Independent review found no issue in the lifecycle correction.

These are subsequent automated lifecycle checks. Earlier real operator
observations remain historical evidence for their named candidates; no new
manual foreground/keyboard observation is claimed. The earlier VSIX hash for
`a6a3cce` does not identify this changed source. Final package proof for the
review-fix commit is recorded in PR #175 before publication preparation resumes.

## Reproduction and repair

Windows could not cold-start the registered native callback class. Both the
agent's direct native probe and the operator's Windows PowerShell 5.1 probe
returned `0x80040154` with no COM object. Starting the existing signed helper
with `-Embedding` made native COM activation and callback delivery succeed.
The reason Windows rejects cold activation remains unresolved.

The extension now owns two callback helpers while notification correlations
remain. It renews alternating helpers every 25 seconds, retaining the previous
registration for a two-second overlap. The pinned helper exits after a callback
or 60 seconds ([KDE source](https://github.com/KDE/snoretoast/blob/v0.9.0/src/snoretoasts.cpp),
fetched 2026-10-17). This removes reliance on cold activation while the owner is
open; it does not repair Windows COM registration.

No native binary or runtime dependency changes. Helpers remain scoped to their
extension host and callbacks retain their owning pipe/session correlation.
Normal disposal terminates owned helpers; failed termination is reported and
ownership retained for a later disposal attempt or the helper's native expiry.
The existing seven-day correlation expiry bounds abandoned notification state.

before focusing the terminal. Loading renderers focus their selected terminal
during initial hydration. Real keyboard-input retesting remains required.
