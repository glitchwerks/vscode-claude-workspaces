# 0.9.0 notification activation fix verification

Dates: 2026-10-17 through 2026-10-20. Tracking: #174; parent release validation: #171.
Base: `92ddd1c1464e0b5b8d29d0e6aac3c3eb847d355f` on `prerelease/0.9.x`.
This record covers the activation repair; the earlier failed real-toast
observations on #171 remain valid historical evidence.

## Reproduction and repair

Windows could not cold-start the registered native callback class. Both the
agent's direct native probe and the operator's Windows PowerShell 5.1 probe
returned `0x80040154` with no COM object. Starting the existing signed helper
with `-Embedding` made native COM activation and callback delivery succeed.
The reason Windows rejects cold activation remains unresolved.

The extension now owns two callback helpers while notification correlations
remain. It renews alternating helpers every 25 seconds, retaining the previous
registration for a two-second overlap. The pinned helper exits after a callback
or 60 seconds ([KDE source](https://github.com/KDE/snoretoast/blob/v0.9.0/src/snoretoasts.cpp),
fetched 2026-10-17). This removes reliance on cold activation while the owner is
open; it does not repair Windows COM registration.

No native binary or runtime dependency changes. Helpers remain scoped to their
extension host and callbacks retain their owning pipe/session correlation.
Normal disposal terminates owned helpers; failed termination is reported and
ownership retained for a later disposal attempt or the helper's native expiry.
The existing seven-day correlation expiry bounds abandoned notification state.

The subsequent fresh-toast test established delivery: launch at 23:39:37 UTC,
matched banner timeout at 23:39:50, and matched click at 23:42:46.495. Panel
focus completed and the target session was active at 23:42:46.496. The operator

renewed throughout the wait and stopped after the click consumed the final
correlation. See [the traced result on #174](https://github.com/glitchwerks/vscode-claude-workspaces/issues/174#issuecomment-6279840922).

This isolates the remaining gap to native window attention. The original
selection path only invoked the contributed panel-focus command and session
manager; it did not request native window focus. The owner approved requiring
VS Code 1.128.0 for 0.9.0. The replacement path uses that version's
[`workbench.action.focusWindow`](https://github.com/microsoft/vscode/blob/1.128.0/src/vs/workbench/electron-browser/actions/windowActions.ts#L410-L430)
after selecting the still-live target, with another liveness check after
awaited panel reveal. It targets the calling workbench's window. This command
requests native focus; its completion does not prove foreground activation or
visible taskbar attention. The real-toast retest is recorded below.

No foreground-window capture, window-title/PID guessing, URI routing, new
native helper or additional dependency was added. The historical 1.120.0 test
and package evidence above predates the approved minimum-version increase;
the minimum integration fixtures now use 1.128.0. Stable 0.8.1 is unchanged.
