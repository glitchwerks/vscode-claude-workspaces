## Reproduction and repair

Windows could not cold-start the registered native callback class. Both the
agent's direct native probe and the operator's Windows PowerShell 5.1 probe
returned `0x80040154` with no COM object. Starting the existing signed helper
with `-Embedding` made native COM activation and callback delivery succeed.
The reason Windows rejects cold activation remains unresolved.

The extension now owns two callback helpers while notification correlations
remain. It renews alternating helpers every 25 seconds, retaining the previous
registration for a two-second overlap. The pinned helper exits after a callback
or 60 seconds ([KDE source](https://github.com/KDE/snoretoast/blob/v0.9.0/src/snoretoasts.cpp),
fetched 2026-10-17). This removes reliance on cold activation while the owner is
open; it does not repair Windows COM registration.

No native binary or runtime dependency changes. Helpers remain scoped to their
extension host and callbacks retain their owning pipe/session correlation.
Normal disposal terminates owned helpers; failed termination is reported and
ownership retained for a later disposal attempt or the helper's native expiry.
The existing seven-day correlation expiry bounds abandoned notification state.

The existing manager skips publication when the target is already selected and
no unread state changes. The provider only sends an active-session update when
the selected ID changes, and the renderer ordinarily focuses the terminal while
rendering. An already-selected notification target therefore has no explicit
input-focus handoff. The correction sends a closed-protocol, session-targeted
terminal-focus intent after awaited native-window attention. Host and renderer
guards reject closed/inactive targets; the renderer dismisses any session menu
before focusing the terminal. Loading renderers focus their selected terminal
during initial hydration. Real keyboard-input retesting remains required.

The new callback-to-webview regression failed in a real VS Code 1.128.0 host
before the correction because no focus intent was posted. Unit regressions also
failed before correction for the missing selection callback and protocol
message. A deferred-promise regression rejects removal of the native-window
await, verifying that terminal focus follows window attention.

### Failed Search-to-Claude input retest and diagnostic boundary

The operator repeated the foreground check after putting keyboard focus in
VS Code Search. The new real toast was requested at 2026-10-21 00:47:58.895 UTC
and clicked at 00:49:28.713 (89.818 seconds later). Panel reveal, session

completed in the host trace by 00:49:28.735. The operator reported that Down
Arrow still did not reach Claude without clicking its terminal. The terminal
focus repair therefore remains unverified and the manual check remains failed.

The diagnostic build now acknowledges the focus intent from the actual embedded
document, immediately and after 500 ms. Its debug record contains only phase,
`documentHasFocus` and `terminalHasFocus` booleans. The latter measures whether
the document's active element is inside the target terminal; it does not prove
xterm keyboard delivery. The observer does not retry focus, is cancelled on
disposal/replacement and ignores stale targets. This distinguishes absent
renderer delivery, an unfocused document and focus lost after a request.

VS Code's [webview focus implementation](https://github.com/microsoft/vscode/blob/1.128.0/src/vs/workbench/contrib/webview/browser/webviewElement.ts#L936-L980)
uses a separate delayed outer-frame focus path with guards against another
input retaining focus (fetched 2026-10-20). That is relevant source evidence,
not a confirmed cause of this operator result. No further focus behavior is
being guessed from passing fake-webview tests. Diagnostic typing acceptance
remains pending.
