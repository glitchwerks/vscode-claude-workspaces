## Method and privacy

The opt-in runner starts owned CLI processes through production `NodePtyFactory`, in isolated fixture directories. Import/default execution starts no native/model work. Live runs require `--run-live` and an absolute executable; fixed Haiku scenarios additionally require `--allow-model`. Only controlled fixture prompts are admitted. Probe code does not rewrite user settings or replace the configured CLI. Product scenarios additionally load the shipped plugin and exercise the production adapter. ## Private adapter checkpoint (2026-10-31)

The Windows, same-host adapter uses a private per-host/per-generation filesystem channel with random authentication, exact target/envelope validation, bounded frames, one request deadline and submission-ID deduplication. Only an authenticated prepared receipt permits native queue keys. Ambiguous delivery is never retried. Disposed and recognized dead-process channels are cleaned without deleting live or foreign directories. Ordinary launch falls back unchanged when unsupported. [`src/composer/composerBroker.ts:L1-L248`; `src/composer/claudeComposerAdapter.ts:L1-L190`; `test/unit/composerBroker.test.ts:L1-L150`; `test/unit/claudeComposerAdapter.test.ts:L1-L117`]

## Controller and protocol checkpoint (2026-10-31)

The controller debounces per-session drafts, flushes before switching/hiding/closing, validates current UUID/generation, and preserves the terminal-only path for missing identities. Unsupported sending versions can still edit/save UUID-backed drafts. Exact-key browser-safe codecs reject unrecognized authority and malformed nested payloads; oversized editable drafts reach an explicit storage-error response rather than disappearing silently. [`src/composer/composerController.ts:L1-L237`; `src/panel/composerProtocol.ts:L1-L151`; `test/unit/composerController.test.ts:L1-L168`; `test/unit/composerProtocol.test.ts:L1-L73`; `src/composer/composerStore.ts:L1-L347`; `test/unit/composerStore.test.ts:L1-L259`; #145]

Native acceptance records history and clears only an unchanged revision. Both history persistence and clearing recheck the current generation across external storage I/O; a change during a write rolls the mutation back. Typing during a clear is retained. Accepted delivery followed by local write failure remains accepted with a storage error, while unconfirmed delivery preserves text and cancels sends queued before that uncertain outcome. No automatic retry is introduced. [`src/composer/composerController.ts:L1-L237`; `src/panel/composerProtocol.ts:L1-L151`; `test/unit/composerController.test.ts:L1-L168`; `test/unit/composerProtocol.test.ts:L1-L73`; `src/composer/composerStore.ts:L1-L347`; `test/unit/composerStore.test.ts:L1-L259`]

Failed-save drafts remain discoverable through volatile, text-free recovery metadata in the current host. Durable reads and restart recovery never claim a failed write succeeded. Restore validates a nonlive expected revision and root before launch, makes a volatile source durable first, and commits destination plus source deletion together; source text survives failed destination writes. UI recovery enumeration is wired in Task 8. Targeted verification passed 113 related tests, full TypeScript compilation and lint; the full prior adapter regression remains the historical 1,052-unit checkpoint. [`src/composer/composerController.ts:L1-L237`; `src/panel/composerProtocol.ts:L1-L151`; `test/unit/composerController.test.ts:L1-L168`; `test/unit/composerProtocol.test.ts:L1-L73`; `src/composer/composerStore.ts:L1-L347`; `test/unit/composerStore.test.ts:L1-L259`; #145]

It supports a remembered adjustable split, temporary expansion, CodeMirror multiline editing/history/find/replace, IME-aware send suppression, and save/delivery feedback.
