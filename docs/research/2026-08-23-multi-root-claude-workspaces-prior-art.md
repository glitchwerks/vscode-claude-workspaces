## Idea

Build a Claude Code plugin (and/or companion VS Code extension) that makes a set of related VS Code multi-root workspace folders behave, from Claude's perspective and the user's UI, like one coherent working context — without merging them into a single repo.

## Requirements

The candidate must address one or more of:

1. **Cross-workspace awareness** — a Claude session launched in one workspace root automatically knows about sibling workspaces in its group.
2. **Workspace-level `CLAUDE.md`/skills scope** — an instructions/skills layer between global (`~/.claude`) and single-repo (`<repo>/CLAUDE.md`), applying to a *group* of related workspaces.
3. **Cross-workspace skill discovery** — Claude can find/invoke skills defined in any workspace in the group, not just the one it was launched in.
4. **Flexible launch with a default root** — launch Claude in any workspace root in the group, with a configurable default root used when none is specified.
5. **Managed workspace tabs in the VS Code UI** — a sidebar/bottom-bar surface for seeing/switching between the group's active Claude sessions.

Non-goals for a candidate to count as "relevant": generic monorepo build tooling (Nx/Turborepo) with no AI-assistant angle; single-repo CLAUDE.md tutorials. Git-worktree-only session managers are borderline, not a hard non-goal — several surfaced as the closest available UI/config analogs for capabilities 4/5 even though a worktree is a branch of one repo, not a sibling repo; they're kept and flagged per-candidate as "pattern transfers, code doesn't."

A plugin that assumes settings.json-configured directories behave like `--add-dir` will silently under-deliver on requirement 3.
- **Lift effort:** study-only (informs the underlying mechanism a plugin would wrap, not a dependency).

### 9. VS Code native multi-root workspace API (`.code-workspace`, `workspace.workspaceFolders`, `onDidChangeWorkspaceFolders`) — the substrate, not a solution

- **URL:** https://code.visualstudio.com/docs/editing/workspaces/multi-root-workspaces (fetched 2026-08-23, page last modified 2026-08-19); https://github.com/microsoft/vscode/wiki/Adopting-Multi-Root-Workspace-APIs (fetched 2026-08-23); https://code.visualstudio.com/api/extension-guides/tree-view (fetched 2026-08-23)
- **Relevance:** provides the underlying hooks that satisfy part of the "flexible launch with a default root" ask (requirement 4) and the data-gathering half of a requirement-5 sidebar — `workspace.workspaceFolders` enumerates all roots in a `.code-workspace` file, `workspace.onDidChangeWorkspaceFolders` fires on add/remove, and `workspace.getWorkspaceFolder(uri)` maps a resource back to its owning root. Settings can be resource-scoped (per-folder) via `workspace.getConfiguration(section, resourceUri)`. **Directly answering the "does VS Code expose a native TreeView/sidebar hook for this" question: no.** The TreeView/TreeDataProvider extension guide was fetched and confirms the API is workspace-folder-agnostic by design — its own canonical sample (`NodeDependenciesProvider`) hardcodes `vscode.workspace.workspaceFolders[0]`, i.e. the first folder only, and the guide documents no `workspaceFolderCount`-scoped view contribution point or any built-in mechanism to aggregate items across folders into one view. A multi-root-aware sidebar is achievable (nothing blocks a `TreeDataProvider` from calling `workspace.workspaceFolders` itself and building a multi-root tree), but it is bespoke logic the extension author writes, not a capability VS Code hands you.
- **Maturity:** core, stable, long-standing VS Code API — not going anywhere.
- **Worth borrowing:** `workspace.workspaceFolders` + `onDidChangeWorkspaceFolders` + `getWorkspaceFolder(uri)` as the mechanical basis for detecting "which roots are in this group" and reacting to changes; resource-scoped configuration as the mechanism for a "default root" setting scoped per `.code-workspace` file (directly relevant to requirement 4, and it already exists — no new VS Code core capability is needed for the default-root selection itself). For requirement 5, the `TreeDataProvider`/`window.registerTreeDataProvider` contract itself is the reusable primitive — a custom provider can walk `workspace.workspaceFolders` and build the "root → sessions" tree the way `vana123.vswt` (candidate 3) builds "repo → worktree → session."
- **What to avoid:** there is no native VS Code concept of a root "group" beyond what's listed in one `.code-workspace` file — if the five capabilities need to span *multiple separate* `.code-workspace` files/windows (as opposed to one workspace file with several roots), this API does not cover that; window-to-window awareness is out of scope for this API surface entirely. Also don't expect a ready-made multi-root TreeView contribution point — confirmed absent; the aggregation logic must be written.
- **Lift effort:** drop-in (these are stable public VS Code extension APIs, not a third-party dependency — "using" them is just writing extension code against the documented contract; the multi-root *aggregation* logic on top is build-from-scratch, not drop-in).

## No prior art found

- **Requirement 2 (workspace-level `CLAUDE.md`/skills scope, as a shipped, machine-enforced layer)** — searched all axes; found only manual/documented conventions (the bootstrap-repo + negated-gitignore pattern from Sahaj.ai/karun.me, candidate 6) and a different tool's proprietary analog (Cursor's nested rules, candidate 8). No Claude Code plugin or extension was found that mechanically inserts a fourth CLAUDE.md tier between global and project scope for an explicitly-defined *group* of sibling repos. This is confirmed as a genuine gap by Claude Code's own hierarchy documentation, which lists only global → project → subdirectory (plus an org-managed layer orthogonal to this use case).
- **Requirement 3 (cross-workspace skill discovery, reliably)** — the one native mechanism that partially covers this (`--add-dir` loading `.claude/skills/` from added folders) is confirmed broken when configured via `settings.json`'s `additionalDirectories` rather than the CLI flag (issue #43267, closed duplicate without a stated fix timeline). No plugin or extension was found that reliably merges skill catalogs across independently-rooted sibling workspaces. Expect original design work here regardless of which underlying primitive (CLI flag vs. settings) is chosen.
- **Requirement 1 + 4 combined as a persisted, named "workspace group" concept in Claude Code itself** — a feature request for exactly this (`.claude-workspace` file, auto-detected, portable/checked-into-repo, #45643) was filed and closed `duplicate` on 2026-04-12 (`unverified: duplicate-of target not stated in the fetched issue`); the closely-related, broader multi-repo workspace request (#35362) was closed by its own author with no fix shipped, and the Desktop-specific version (#56853) remains open and upvoted as of 2026-07-21. Net: no version of this request has resulted in a shipped Anthropic feature. No third-party plugin was found that reimplements this persistence layer for Claude Code specifically (SommeSi/claude-workspaces, candidate 5, comes closest but is scoped to worktree-based task isolation, not sibling-repo grouping; yazilim-vip.claude-workspace, candidate 1b, comes closest on the "auto-add every folder" mechanic but has no persisted/named group or default-root concept).
