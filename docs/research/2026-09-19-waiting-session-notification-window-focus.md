## Idea

Notify the user with a native Windows notification when a managed Claude Code session (run as a PTY inside `vscode-claude-workspaces`) is waiting for input and its owning VS Code window is unfocused; clicking the notification must focus the correct window, reveal the panel, and activate the specific waiting session, with dedup across repeated wait signals — for issue [glitchwerks/vscode-claude-workspaces#51](https://github.com/glitchwerks/vscode-claude-workspaces/issues/51).

## Requirements

1. Detect "waiting for input" reliably — the issue's own technical notes say to investigate Claude Code hooks / structured events before relying on terminal text matching.
2. Send a native Windows OS-level notification (not `vscode.window.show*Message`) when the owning window is unfocused/minimized; suppress it when the owning window is already focused.
3. Clicking the notification restores/focuses the owning VS Code window, reveals the Claude Workspaces panel, and activates the specific waiting session.
4. In a multi-window scenario, route the notification (and the click) to the window that actually owns the waiting session — there is no existing IPC between extension-host windows in this codebase.
5. Dedupe repeated notifications for one wait state; don't re-notify on every stdout chunk.
6. Constraint: Windows-only is in scope (explicitly out of scope for other platforms). Must work inside VS Code's extension-host sandbox. Prefer not requiring the user to separately install an additional native binary/module (e.g., a PowerShell module they must `Install-Module`).

- **Problem-shape synonyms** — "background task done notification VS Code", "bring window to foreground from background process Windows"
- **Adjacent domains** — Electron multi-window/multi-instance toast activation (COM activator, `ToastActivatorCLSID`), Windows shell/AppUserModelID notification routing

- **Negative axes** — excluded macOS/Linux-only notification tooling except where the same repo also documents its Windows-specific behavior (needed for direct comparison); excluded generic "desktop notification library" results with no click-routing or multi-window story

## Shortlist (ranked by expected value)

### 1. dimokol/claude-notifications — VS Code extension + Claude Code hooks; per-workspace signal files as inter-window "IPC"; documents and fails to solve the Windows foreground-raise problem

- **URL:** https://github.com/dimokol/claude-notifications (commit `18ac7bdcb84c023f5852b5633243f0bf6dfda85f`, v3.7.0, fetched 2026-09-19)
- **Relevance:** addresses requirements 1, 2, 4, 5 with working, shipped code; requirement 3 is only **partially** addressed — see "What to avoid" below, this is the load-bearing negative finding for the whole idea.
- **Maturity:** actively pushed (last commit 2026-09-08, ~5 months of history since 2026-04-05), MIT license, single maintainer, VS Code Marketplace listing, `npm run test` / CI referenced in `package.json`. `devDependencies` is esbuild only — the shipped extension has **zero runtime npm dependencies** (README: "zero external dependencies"); it does not depend on `node-notifier` or any PowerShell module the user must install.
- **Worth borrowing:**
  - **Detection via hooks, not text matching** — installs `Stop`, `Notification`, `PermissionRequest`, and `PreToolUse` (matcher-scoped to `AskUserQuestion`) hooks into `~/.claude/settings.json`, read from `README.md § How the Hook Works`. This is a real answer to the issue's "investigate Claude Code hooks" note, and — important — it targets the **CLI-driven `claude` process**, not the official Claude Code VS Code extension, which is architecturally the same shape as `vscode-claude-workspaces`' PTY model (see requirement-3 discussion below).
  - **Filesystem-as-cross-window-IPC, keyed by workspace identity, with no window-to-window channel at all.** Per `README.md § How the Hook Work`s: the hook hashes the workspace root (`sha1(workspaceRoot)` → 12 hex chars) and writes a JSON signal file to `~/.claude/focus-state/<hash>/`. Each VS Code window's extension only watches the hash directory for *its own* workspace — the owning window self-selects; no window needs to know about any other window. This is a direct, concrete answer to "no existing IPC between extension-host windows."
  - **Atomic single-fire race for dedup + exactly-one-notification guarantee.** The hook writes the signal, sleeps 1.2s, then the extension (if VS Code is focused) or the hook itself (if not) races to claim a marker file via `O_EXCL` — whichever claims first is the one that fires. README: "Exactly one notification path fires per stage: never zero, never two for the same stage." This single mechanism answers both "suppress when owning window is focused" and "dedupe repeated notifications."
  - **Stage-ID dedup semantics.** A "stage" only advances on an explicit user acknowledgment (notification/toast click) or a genuinely new hook event; re-fires of the same underlying event within the same stage are silently dropped (`hook.js` step 4, README). `UserPromptSubmit` is used purely to bump the stage ID so the next `Stop`/`Notification` is treated as fresh.
  - **PID-ancestor-chain identification of the exact terminal/session**, so the click can activate the specific tab/session, not just the workspace (README § How the Hook Works, step 5).
- **What to avoid / critical negative finding for requirement 3:** The extension's own source explicitly documents that it **could not** bring the VS Code window to the foreground from a Windows toast click, and gave up trying. From `extension.js` (fetched 2026-09-19, quoted verbatim): *"On Windows, a toast click runs with ShellExperienceHost as the foreground window, which the OS shields — no SetForegroundWindow / AttachThreadInput / keystroke trick can raise a window over it from a background process (documented MS limitation)."* `lib/win-focus.js` contains a fully-implemented `AttachThreadInput` + `SendInput`(Alt-tap) + `SetForegroundWindow` retry loop (verified working *outside* the toast-click context, per its own code comment) but has "NO caller in the toast-click path" because it was tried there and failed. The README corroborates: clicking the OS banner "flashes the taskbar instead of raising the window," same as Slack/Discord/Teams toast clicks on Windows, and cites this as consistent with a documented Microsoft limitation and open `microsoft-ui-xaml` issues (#1939, #5499). **This is not solved by routing through VS Code's own `vscode://` URI handler either** — `extension.js`'s `registerUriHandler` callback decodes a `marker` query param and resolves `workspaceRoot`, but performs no window-targeting logic; whichever window VS Code's OS-level URI dispatch happens to deliver the click to is the one that runs the handler (VS Code's own last-focused-window default — see candidate 4 below). The real multi-window routing in this project is the filesystem-signal mechanism above, not the URI handler.
- **Lift effort:** adapt-pattern for detection/dedup/routing (items 1, 2, 4, 5 above are directly portable ideas, not code to vendor); requirement 3's "restore and focus the owning window" sub-clause should be treated as **not achievable** on unpackaged Win32 apps per this evidence — see "No prior art found" below.

### 3. `AllowSetForegroundWindow` + `AttachThreadInput` Win32 pattern (as used in VS Code core and in candidate 1's `win-focus.js`) — the one foreground-raise technique that has been shown to work, but only outside the toast-click activation context

- **URL:** https://github.com/Microsoft/vscode/pull/13255 (VS Code core, merged; fetched 2026-09-19) and https://github.com/dimokol/claude-notifications/blob/18ac7bdcb84c023f5852b5633243f0bf6dfda85f/lib/win-focus.js
- **Relevance:** partially addresses requirement 3 (bringing *a* VS Code window to the front programmatically), but explicitly does **not** solve the "from a notification click" sub-case.
- **Maturity:** VS Code core PR is 2016-era, long since merged and is how `code` (the CLI launcher) reuses/focuses an already-running window today when a second instance starts — a real, load-bearing mechanism in VS Code itself, not a curiosity. `win-focus.js` is 2026, actively maintained, MIT.
- **Worth borrowing:** The technique — `AttachThreadInput` to the current foreground window's thread (merging input queues so Windows grants foreground privilege), `BringWindowToTop` + `SetForegroundWindow`, verified via `GetForegroundWindow()` polling rather than trusting the Win32 return value, executed via a short-lived non-detached `child_process.spawn('powershell.exe', ...)` (detached processes break `AttachThreadInput` inheritance per an explicit code comment dated 2026-05-25) — is a concrete, tested pattern for "raise a specific window by PID" when invoked from a context that is *not itself* the toast/notification activation handler (e.g., a command run from within the already-active extension host, or from `code`'s own second-instance path).
- **What to avoid:** Do not assume this generalizes to the toast-click handler itself — candidate 1's evidence is that it does not, because at toast-click time the calling process is `ShellExperienceHost`/the launcher activated by Windows, not a process the user has just interacted with, and Windows' foreground-lock heuristics specifically shield against that case.
- **Lift effort:** adapt-pattern (the PowerShell child-process shape is portable; the specific pid-discovery `EnumWindows` loop would need adaptation to find `vscode-claude-workspaces`'s target window).

### 4. VS Code `vscode://<publisher>.<extension>` URI handler + `vscode.window.registerUriHandler` — the standard mechanism for "a click outside VS Code activates code inside a specific extension," with a known multi-window caveat

- **URL:** https://code.visualstudio.com/api/references/vscode-api ; https://github.com/microsoft/vscode-extension-samples/blob/main/uri-handler-sample ; https://github.com/microsoft/vscode/issues/79635 (closed 2019-10-21, fetched 2026-09-19)
- **Relevance:** addresses "reveal panel / activate session" (requirement 3's non-window-focus half) once VS Code *is* frontmost; does not reliably address requirement 4 (routing to the *owning* window) — see caveat.
- **Maturity:** first-party, stable VS Code API surface, unchanged in shape since the 2019 `IURLService#create()` work.
- **Worth borrowing:** `registerUriHandler` + `vscode.window.showTextDocument`/`workbench.view.extension.*` command execution is the standard, sandboxed way to react to an external click without any custom protocol/registry work of your own (VS Code already owns the `vscode://` scheme registration). Candidate 1's `extension.js` demonstrates the pattern end-to-end: decode a `marker` query param, resolve a workspace/session identity from it, then act.
- **What to avoid / open caveat:** `microsoft/vscode#79635` ("vscode:// protocol should allow a windowID parameter to forward to that window, instead of the last focused one") was filed in 2019 noting VS Code "today ... simply open[s] in the last active window, which might not be right," and was closed as completed in the October 2019 milestone against VS Code's **internal** `urlService`/`windowsMainService` (used by `IURLService#create()`). Nothing retrieved in this research confirms that a third-party extension can set an equivalent `windowId` on a `vscode://<publisher>.<ext>/...` URI it hands to the OS to steer delivery to a non-last-focused window — mark this `unverified` for extension-facing use. Candidate 1's own `extension.js` UriHandler callback (fetched 2026-09-19) contains no window-targeting logic at all and instead falls back to "whichever window happened to receive it," which is consistent with the caveat rather than a demonstrated workaround. Treat window-level routing as owned by candidate 1's filesystem-signal mechanism, not by the URI handler.
- **Lift effort:** drop-in for the reveal-panel/activate-session half of the flow; study-only (do not rely on it) for cross-window routing.

### 5. node-notifier / SnoreToast, `powertoast`/`win11toast` (WinRT), and BurntToast — three families of "how do you actually put a toast on Windows" that trade off dependency footprint against reliability

- **URL:** https://github.com/mikaelbr/node-notifier (last push 2024-06-24 — stale relative to 2026-09-19); https://github.com/xan105/node-powertoast; https://github.com/GitHub30/win11toast; BurntToast (PowerShell Gallery module, `witit.blog`/`4sysops.com` write-ups, fetched via search 2026-09-19)
- **Relevance:** addresses requirement 2 only (the notification-emission mechanism, not click-routing or focus).
- **Maturity:** `node-notifier` is the long-standing default (used inside `vscode-terminal-osc-notifier` and referenced by several other extensions found in this search) but is functionally dormant — no push in over two years as of this research date. `powertoast`/`win11toast` are more actively positioned as "no native module required, PowerShell-VM fallback with optional NodeRT precompiled bindings for speed" — from training, not independently verified for current maintenance status in this session.
- **Worth borrowing:** None of these solve requirement 3/4; they are purely the "how do bytes become a Windows toast" layer, which candidate 1 shows can be done with **zero runtime npm dependencies** (its own bundled launcher, not node-notifier/SnoreToast) — worth noting as an existence proof that the "no separately-installed native binary" constraint is achievable without giving up native toast fidelity.
- **What to avoid:** `node-notifier`'s Windows path shells out to a bundled `SnoreToast.exe` binary inside `node_modules` — this satisfies "user doesn't have to separately install anything" (it's bundled in the npm package) but does add a native `.exe` to the packaged VSIX, with the packaging/signing implications that carries. BurntToast requires the user to have (or the extension to silently `Install-Module`) a PowerShell Gallery module — this is the one option that clearly violates "must not require an additional native binary/module the user has to separately install."
- **Lift effort:** study-only — this is a menu of emission mechanisms to choose among, not a design to adopt wholesale; candidate 1's evidence suggests a bundled-launcher-plus-registry-key approach (or, per the ShellExperienceHost finding, `vscode.window.showInformationMessage` for the fallback in-focus case) is achievable without a runtime dependency at all.

### 6. SnoreToast COM `ToastActivatorCLSID` / `electron-windows-interactive-notifications` — generalizable multi-instance toast-activation-routing pattern (outside VS Code)

- **URL:** https://github.com/KDE/snoretoast (fetched via search 2026-09-19); https://github.com/felixrieseberg/electron-windows-interactive-notifications
- **Relevance:** answers requirement-4's *generic* shape ("route a click on an OS notification back to the correct one of several running instances of the same desktop app") for apps that control their own packaging/registration, which VS Code extensions do not.
- **Maturity:** SnoreToast is a mature, widely-embedded CLI (used by node-notifier itself); `electron-windows-interactive-notifications` is an established Electron community package from a former Electron/Slack engineer, oriented at wrapping the same underlying WinRT `ToastNotificationManager` + COM activation surface.
- **Worth borrowing:** The general mechanism — Windows checks the calling binary's Start Menu shortcut for a `System.AppUserModelID` + `System.AppUserModel.ToastActivatorCLSID`, and if present, routes toast-click activation through a registered COM `INotificationActivationCallback` component rather than a plain process launch — is the *documented, supported* way multi-instance Win32 apps disambiguate "which instance should this click go to." It requires the app to own an installed shortcut with those properties, i.e., requires packaging control the app installs for itself.
- **What to avoid:** This mechanism is out of reach for a VS Code *extension* — `vscode-claude-workspaces` doesn't control `Code.exe`'s Start Menu shortcut or `AppUserModelID`, and installing a separate COM-registered helper app to own the toast identity would be a meaningfully larger surface (registry writes, a persistent activation server) than anything found in candidate 1. Listed here as the generalizable pattern the issue asked about (research axis 4), not as something directly usable inside the extension-host sandbox.
- **Lift effort:** study-only.

## Follow-up (2026-09-19): reconciling with the Claude Desktop / ChatGPT Desktop counter-example

The user pushed back that Claude Desktop and ChatGPT Desktop reliably foreground their window on a Windows toast click, and asked whether this is the same problem as the VS Code case or a different one.

**Verdict: same underlying Windows mechanism, different identity class — and that difference is the reconciling fact.** Claude Desktop and ChatGPT Desktop are not "an Electron app that happens to get lucky with SetForegroundWindow"; on Windows both ship with **package identity** (MSIX / Store install), which puts toast-click activation through a Windows-managed COM activation path that unpackaged Win32 processes (including `Code.exe` and anything a VS Code extension can do from inside it) do not have access to. This is a narrower and more useful answer than "it's flaky for everyone," and it directly explains why the user observes 100% reliability from the two Electron apps while `dimokol/claude-notifications` observes 0%.

**1–2. What "toast activation grants foreground rights" actually means, and to whom.** It is not a blanket grant to "any app that gets a toast" — it is a Windows-managed activation path available specifically to apps with **package identity** (full MSIX, or a "sparse package" that grants identity to an otherwise-unpackaged exe) that register a COM `ToastActivatorCLSID` on their app manifest/shortcut. Microsoft Learn's `System.AppUserModel.ToastActivatorCLSID` property doc (fetched 2026-09-19: https://learn.microsoft.com/windows/win32/properties/props-system-appusermodel-toastactivatorclsid) and the UWP→WinUI migration guide (fetched 2026-09-19: https://learn.microsoft.com/windows/apps/windows-app-sdk/migrate-to-windows-app-sdk/guides/toast-notifications) both describe this path: a click routes through `INotificationActivationCallback.Activate` (or `ToastNotificationManagerCompat.OnActivated`) inside the *registered, package-identified* process — for classic UWP apps window activation is automatic ("Your window is automatically brought to foreground when foreground activation occurs"); for WinUI/Windows App SDK apps the app must still call the foreground API itself, but it does so **from inside the COM-activated, package-identified process**, which Windows recognizes as an authorized activation rather than an arbitrary background call. Confirmed empirically: `Claude_pzs8sxrjxfjjc!Claude` is a `PackageFamilyName!AppId`-shaped AUMID, and Claude Desktop for Windows is documented as installing and running as an MSIX/AppX package in the protected `WindowsApps` folder, launchable only via its AUMID or `claude://` protocol (`anthropics/claude-code#69353`, `#47877`, Claude Help Center "Deploy Claude Desktop for Windows," fetched 2026-09-19: https://support.claude.com/en/articles/12622703-deploy-claude-desktop-for-windows). ChatGPT Desktop is likewise distributed as a Store-signed MSIX (Microsoft Store product `9NT1R1C2HH7J`; ChatGPT Learn "Deploy the Windows app," fetched 2026-09-19: https://learn.chatgpt.com/docs/enterprise/windows-deployment). Both apps' reliable foreground-raise is consistent with using this packaged-identity activation path, not with a generic OS courtesy extended to any toast-clicking process.

**3. Unpackaged Win32 apps have no equivalent path, and this is where the flakiness comes from.** For an app with **no** package identity (a bare `.exe` with only a Start Menu shortcut carrying a plain `System.AppUserModel.ID`, per "How to enable desktop toast notifications through an AppUserModelID," fetched 2026-09-19: https://learn.microsoft.com/windows/win32/shell/enable-desktop-toast-with-appusermodelid), there is no COM-activation foreground grant — the click just relaunches/signals the app via ordinary command-line or protocol activation, and `SetForegroundWindow`'s general eligibility rules apply with no special exception (Microsoft Learn, `SetForegroundWindow` Remarks, fetched 2026-09-19: https://learn.microsoft.com/windows/win32/api/winuser/nf-winuser-setforegroundwindow#remarks; Raymond Chen, "Foreground activation permission is like love: You can't steal it, it has to be given to you," fetched 2026-09-19: https://devblogs.microsoft.com/oldnewthing/20090220-00/?p=19083). This is exactly the gap Electron apps hit when they ship *without* the MSIX/sparse-package + `ToastActivatorCLSID` setup: `electron/electron#4766` ("Clicking notification on Windows doesn't focus the app even with window.focus in click handler," fetched 2026-09-19) and `#24524` document it, and the standard workaround — a synthetic **dummy keystroke** via `SendInput` sent to the app's own window immediately before `SetForegroundWindow`, to manufacture the "calling process received the last input event" eligibility condition — is packaged as the userland `windows-dummy-keystroke` npm module (https://dev.to/randomengy/allowsetforegroundwindow-quirks-12og, fetched 2026-09-19). `electron/electron#36635` ("requestSingleInstanceLock does not allow foreground focus when launched via notification on Windows") was fetched directly and confirmed **closed as not planned** by the Electron maintainers (fetched 2026-09-19: https://github.com/electron/electron/issues/36635) — i.e. Electron declined to fix this at the framework level, leaving app authors to either adopt package identity or implement the dummy-keystroke workaround themselves. This is consistent with the reconciliation: apps that skip package identity are the ones that stay flaky.

**4. Does VS Code's multi-window/multi-process topology matter, independent of the above?** Somewhat, but less than the prior report implied, and it is not the primary explanation. VS Code runs **one shared main Electron process per running instance** — `code <path>` from a second terminal signals the existing main process rather than spawning a new one, and each window is a renderer process owned by that same main process (`microsoft/vscode#13255`, cited in candidate 3, uses exactly this to raise an *existing* window from a second CLI invocation). So VS Code windows are not independent OS-level apps the way two unrelated Electron apps are; the real gap is that the code responding to a Claude-notification click — the extension host (a separate Node child process with no HWND of its own) or a spawned helper — is never the main process that owns the target window, and VS Code's extension API exposes no primitive for asking the main process to raise a specific window on the extension's behalf. `Code.exe` itself is also, in the typical (non-Store) install, an unpackaged Win32 app with no `ToastActivatorCLSID` of its own, so even VS Code core has no packaged-identity activation path to lean on here.

**Was the specific Chromium-style sequence tried and ruled out for VS Code, or is it untested?** Candidate 1's README ("Help wanted: Windows banner-click window focus," fetched 2026-09-19: https://github.com/dimokol/claude-notifications/blob/main/README.md) lists techniques already tried: `SetForegroundWindow`, `AttachThreadInput`, `SendInput`/Alt-key, `SwitchToThisWindow`, "a shell-launched handler with the activation grant," `ForegroundLockTimeout=0`, and routing through VS Code's own `vscode://file/` core activation — all reduced to a taskbar flash. However, `SendInput`/Alt-key reads as the `AttachThreadInput` alt-tap technique, which is **not the same sequence** as the specific Chromium/Electron workaround documented above (a dummy keystroke delivered to the *toast-activated process's own window* to manufacture "received last input" eligibility for **that process**, followed by `AllowSetForegroundWindow(Code.exe PID)` from that same eligible process, then signaling `Code.exe` to raise itself). Candidate 1's `claude-notif://` launcher — a real Win32 process with its own window created purely to run this sequence — would be the natural place to run it, but nothing retrieved confirms this exact sequence was attempted. **This is the one concrete, cheap spike worth timeboxing before relaxing the AC**, not a technique that has been ruled out.

**Bottom line for the AC:** "Clicking the notification foregrounds the correct VS Code window" is not achievable via the packaged-identity/COM-activation path Claude Desktop and ChatGPT Desktop use, because that path requires package identity (MSIX or sparse package + registered `ToastActivatorCLSID`) that neither `Code.exe` nor a VS Code extension can supply from inside the extension-host sandbox — building it would mean shipping and registering a separate, independently-installed helper application (candidate 6's mechanism), a materially larger investment than "install a VS Code extension." What remains genuinely open, and cheap to test before committing to that larger investment, is the precise Chromium-style dummy-keystroke + `AllowSetForegroundWindow(Code.exe PID)` sequence run from candidate 1's own unpackaged `claude-notif://` launcher process — candidate 1's own investigation does not appear to have tried that exact sequence, only the `AttachThreadInput`/alt-tap variant.
